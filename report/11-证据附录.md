# 11. 证据附录

## G4 逐项判断

G4 的判定单位是单个 case，而不是一张汇总图。每个 case 必须同时具备输入配置、模型输出、validation mode、后端 observed、误差百分比、pass/blocked 状态和 stderr 路径。15 个 `real` case 真实执行了低内存建索引；5 个 `real-threshold` case 在大内存检查点前降低 `maintenance_work_mem`，避免开发机 OOM。两类都捕获了完整的 pgvector 原始错误，只有后者不声称完成巨型索引。

| 判断项 | 通过标准 | 实际结果 |
|---|---|---|
| 覆盖率 | 固定矩阵至少 20 组 | 20 组 |
| 模式纪律 | large 不得伪装为 real | 15 real + 5 real-threshold |
| 后端证据 | 每组有原始 stderr | 20/20 有文件 |
| 数值误差 | absolute relative error <5% | 20/20 为 0.0000% |
| 旧公式对照 | 至少四个失效场景 | old-fail-01..04 全部包含 |

## 旧公式为何失效

低 lists 场景中旧公式主要按行数和维度粗略估计，可能高估几十到几千 MB；当 lists=8192 或 32768 时，`lowerBoundSize=4*N*C` 和距离矩阵项成为主导，旧公式反而低估到 1,594 MB 与 1,850 MB。新模型把 samples 的目标容量和实际样本数分开计算，因而同时解释 10 MB、7,147 MB 和 17,459 MB 三种量级。

## G10 审计不越界

零参数审计输出的 rows 来自 `pg_class.reltuples`，这只是统计估计；lists 来自 `reloptions`，dims 来自 `atttypmod`，索引类型来自 `pg_am`。因此输出可以回答“目录中记录了什么”和“静态配置是否有风险”，但不能回答某一条业务 SQL 的实际计划。`possible_seqscan` 的布尔值必须与 EXPLAIN 分开呈现，HNSW 的 lists/probes/内存列必须保持空值。

## W0 安全基线

输入验证先于 psql 调用。`LISTS`、`PROBES`、`ROW_COUNT` 和 `DIMS` 仅接受正整数，内存设置仅接受数字加受限单位；注入字符串在 shell 层返回非零退出码。SQL 函数使用固定 `search_path`，schema version 表记录迁移版本。安全检查是诊断工具可信度的前置条件，不与 G4 数值通过混为一个门禁。

## 证据链复核

最终复核顺序为：先执行 shell 输入测试，再校验 SQL 文件和 schema version；然后运行矩阵验证器，逐行对照 `raw-memory-errors/`；最后运行零参数审计并保存事务回滚日志。若端点不可达，报告只能记录 model-only；若端点返回非预期错误，记录 fail 并保留 stderr。任何情况下都不能把 predicted 值写入 observed 列。

## 复核者可执行的最小路径

评审者不需要先相信 PDF：先运行 `tests/test_input_validation.sh`，确认注入退出码为 2；再打开 `docs/04-数据与图表/raw-memory-errors/old-fail-04.log`，确认 `memory required is 17459 MB` 的原始文本；最后对 `report/figures/data/memory_model_matrix.csv` 执行独立求和，检查 predicted 与 observed 两列一致。若需要验证零参数边界，读取 `tests/audit-zero-param-20260818.log` 并查找 `pronargs=0`、HNSW 空字段和事务回滚。

这条路径将“代码可审查、数据可重算、后端日志可追溯”拆成三个独立动作。任何动作失败都应降低结论等级，而不是用报告中的图表替代缺失证据。
