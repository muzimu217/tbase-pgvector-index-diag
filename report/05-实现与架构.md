# 5. 实现与架构

实现采用独立 schema 的纯 SQL/plpgsql 工具集，不修改 pgvector 扩展 ABI。数据流为“系统目录 → 参数内省 → 源码模型 → 风险规则 → 审计清单”：`sql/04_catalog_introspect.sql` 建立 `vector_index_catalog`，`sql/02_memory_model.sql` 提供内存解析、lists 推荐和 11 项分配模型，`sql/05_audit.sql` 暴露零参数 `audit_all_vector_indexes()`，shell harness 负责矩阵执行和证据归档。

模型中的关键边界是目标采样容量 `T=max(10000, 50*lists)` 与实际样本数 `N=min(rows,T)` 分开使用。`samplesSize` 按 `T` 分配，`closestCenters`、`lowerBound`、`upperBound` 按 `N` 分配；其余中心、聚合、距离矩阵和计数数组逐项对应源码。总字节除以 1 MiB 后向下取整再加 1，复刻 pgvector 的 `memory required is X MB` 口径。`vector(128)` 的 ABI 尺寸由 `tools/verify_ivfflat_sizes.c` 在目标 x86-64 环境实测为 520 bytes。

审计输出保留索引类型差异：IVFFlat 显示 lists、recommended lists、predicted build memory、maintenance_work_mem 和 recommended probes；HNSW 的 IVFFlat 专属字段留空，并附“IVFFlat-only checks are not applied”说明。`possible_seqscan` 明确标注为 static catalog risk，不伪装成 EXPLAIN 结果。函数定义的 `pronargs=0` 断言证明审计调用无需手工参数。

安全与可交付性是架构的一部分。shell 层只接受正整数和受限内存单位，注入字符串在调用 `psql` 前退出；SQL 函数固定 `search_path = pg_catalog, pg_temp`；schema version 表把 W0/W1/W2 的迁移状态钉死。这样诊断工具本身不会因为不可信输入或 search path 污染改变结论。
