# 2. 背景与任务对齐

## 2.1 问题背景

IVFFlat 建索引同时受 rows、维度、lists、样本容量和工作内存影响。旧诊断公式把不同生命周期的数组按同一行数边界估算，导致在大维度或大 lists 场景严重低估；诊断工具还要求用户手工传参，无法回答“当前数据库中的所有向量索引是否有风险”。这两个缺口分别对应内存模型正确性和运维入口可用性。

项目采用三层证据：源码分配点决定模型，OpenTenBase 后端错误决定观测值，系统目录 SQL 决定零参数审计输入。所有结果通过固定输入矩阵、原始日志和 SHA256 清单归档。模型值绝不写入 `observed_mb`，当端点不可用时 harness 只报告 `blocked` 或模型输出。

## 2.2 任务与验收门槛

`PLAN.md` 定义 W0 安全与语义止血、W1 源码模型、W2 20 组实测验证和 R-12 零参数审计。G4 要求至少 20 组、误差小于 5%、small 与 large 分层、每行指向原始 stderr；G10 要求零参数函数从系统目录取得参数，并回归官方 lists 公式。

| 任务 | 证据 | 结论 |
|---|---|---|
| 内存模型 | `memory-model-matrix.csv`、20 份 raw stderr | 20/20 pass，误差 0.0000% |
| 大场景边界 | `old-fail-03.log`、`old-fail-04.log` | 7147 MB、17459 MB 与模型一致 |
| 零参数审计 | `tests/audit-zero-param-20260818.log` | IVFFlat/HNSW 均识别，`pronargs=0` |
| 官方公式 | `sql/02_memory_model.sql` | ≤1M 用 `CEIL(rows/1000)`，>1M 用 `CEIL(SQRT(rows))`，上限 32768 |
| TAP 基线 | `tests/README.md` 与三次原始日志 | 0/44 通过，1 bailout，43 未执行，不等于 44 失败 |

## 2.3 贡献边界

贡献一是从源码重建并验证 IVFFlat 构建内存模型；贡献二是把目录发现和审计接口收敛为零参数调用；贡献三是把大场景的不可运行性显式建模为阈值验证，而不是编造巨型索引成功记录。项目不宣称所有 PostgreSQL 版本、向量类型和硬件 ABI 都适用，也不把静态目录风险写成查询计划事实。
