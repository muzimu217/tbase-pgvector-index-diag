# 需求调研报告（提纲・证据底稿）

> ⚠️ 评审方提供的提纲与已核实证据底稿（R003 §4.3）。这一路证据质量最高：多家厂商博客出现**同一条报错原文**，而该报错正是 `validate_memory_model.sh` 要捕获的目标文本。成稿要求：复核每条 → **在你自己的环境复现一次低内存建索引，贴你自己的报错原文**（第一手） → 改写 → 去掉本注记。

## 1. 调研目标与方法

目标：论证「索引构建诊断与参数推荐」需求的真实性。方法：MCP 检索（存档表 §6）+ 上游源码核对 + 竞品功能对照。

## 2. 痛点证据（厂商博客第一手报错）

| 来源 | 场景 | 报错/现象 | 说明的问题 |
|---|---|---|---|
| Crunchy Data | lists=2000 | `ERROR: memory required is 1390 MB, maintenance_work_mem is 1024 MB` | 报错只在失败时出现，**事前预测是空白** |
| Aiven | lists=200 | `ERROR: memory required is 405 MB, maintenance_work_mem is 150 MB` | 同一报错跨厂商复现 |
| Stormatics | 1M 行，默认 64MB | `ERROR: memory required is 501 MB, maintenance_work_mem is 64 MB`；原文称"没有官方推荐值" | **参数推荐需求的最直接依据** |
| DEV Community | HNSW 大规模 | 内存不足静默回落磁盘构建，**慢 10–50×**；5M×1536d 需 8–16GB | "构建慢"的根因常是内存不足 |
| Neon | HNSW | `NOTICE: hnsw graph no longer fits into maintenance_work_mem after 100000 tuples … Building will take significantly longer` | HNSW 降级是 **NOTICE 不是 ERROR**，更隐蔽，诊断需求更强 |

## 3. 竞品与生态对照（引用 R001，成稿时浓缩）

- AlloyDB（专有 ScaNN）：`evaluate_query_recall()`、`pg_stat_ann_indexes`——**付费专有能力；开源 pgvector 无等价物**，这就是本项目的定位（不过度 claim：不做"业界首创"类表述，做"开源 pgvector 生态空白"表述）。
- 上游治理先例：PR #765（HNSW 内存估算函数）被拒，维护者 Kane 原话"approximate formula…may be open to including it in the readme, but don't want to add a function"；PR #863（bench harness）被拒 → 诊断做成外部工具形态的依据。
- 官方参数建议只有一句起步值（rows/1000 或 sqrt(rows)），社区只有经验区间（512MB–1GB / 2–4GB），无源码级预测。

## 4. 需求结论

用户在三个时刻需要帮助而今天没有工具：① 建索引前（要多少内存、选多大 lists）② 建索引时（为何慢/卡住）③ 建成后（参数是否合理、召回是否有风险）。→ 导出需求规格说明书 RQ 清单。

## 5. 与方向一的边界

benchmark harness、数据集脚本归方向一；本仓库只做诊断/预测/推荐，跨仓引用用 URL + commit SHA（G18）。
