# pgvector 索引诊断与参数推荐需求调研报告

## 1. 调研结论

pgvector 用户在三个时刻缺少可审计的诊断能力：建索引前不知道需要多少 `maintenance_work_mem`；建索引失败或变慢时不知道是哪个源码检查点触发；索引建成后不知道 lists、probes、统计行数和计划风险是否合理。本项目的切入点是外部 SQL 工具集：从系统目录自动取参，以 pgvector 源码公式预测构建检查点，再输出零参数风险清单。

当前最强证据来自 OpenTenBase 5.0/pgvector 0.8.0 端点的第一手日志，而不是博客中的估算。20 组固定矩阵全部捕获了 `memory required is X MB` 原始错误，预测与 observed 误差为 0.0000%；另有零参数 IVFFlat/HNSW 审计实测。large 组采用阈值触发，不宣称完成巨型索引构建。

## 2. 调研方法

调研分为四步：核对公开生态中的构建内存痛点；对照 pgvector 源码和上游 PR 的治理边界；把用户场景转成 RQ；在授权端点用原始 stderr、系统目录和 SQL 测试闭环。公开资料只说明问题普遍存在，本项目的数字以 `docs/04-数据与图表/`、`tests/` 和 `report/figures/data/` 为准。

## 3. 痛点证据

| 用户时刻 | 公开现象 | 本项目的第一手对应 |
|---|---|---|
| 建索引前 | IVFFlat/HNSW 需要的内存随 rows、dims、lists 变化，社区通常只能事后看到错误 | `sql/02_memory_model.sql` 逐项计算 11 个分配 |
| 建索引时 | `memory required is ...` 错误或 HNSW NOTICE 只在运行中出现 | 20 份原始 stderr，保留前置建表/INSERT/ERROR 链 |
| 建成后 | lists 偏离、统计行数陈旧、HNSW 与 IVFFlat 参数混用 | `audit_all_vector_indexes()` 零参数目录审计 |
| 安全与迁移 | shell 参数可能拼接进 SQL，裸数字单位容易误读 | W0 输入拒绝、裸 `65536`=64 MB、固定 search_path |

公开厂商资料中可以看到类似报错：Crunchy Data、Aiven、Stormatics 的 IVFFlat 文章给出不同 rows/lists 下的 `memory required` 文本；Neon 的 HNSW 资料展示了超出 `maintenance_work_mem` 后的 NOTICE。不同文章的硬件和版本并不相同，因此它们只作为痛点背景，不能替代本项目端点的实测。

## 4. 竞品与上游边界

AlloyDB 等专有产品提供 recall/索引诊断能力，说明“建成后体检”是明确需求；开源 pgvector 生态仍缺少一个从目录自动取参、可解释内存模型和风险清单的轻量工具。上游 PR #765（https://github.com/pgvector/pgvector/pull/765）讨论过 HNSW 内存估算函数，维护者 Kane 的意见是近似公式可以写进 README，但不希望为它新增函数；PR #863（https://github.com/pgvector/pgvector/pull/863）也说明 benchmark harness 不应混入扩展本体。由此确定本项目采用独立 schema 的 SQL 工具，不修改 pgvector 主路径。

## 5. 需求空白与范围

本仓库负责源码级 IVFFlat 构建内存模型、零参数目录审计、lists/probes 起点建议和异常边界；方向一负责查询性能 benchmark，两仓不重复实现。当前模型覆盖 `vector` 类型和已验证的 x86-64 OpenTenBase ABI；halfvec、bit、sparsevec、多节点 EXPLAIN 关联和 W3 构建耗时属于后续需求。

## 7. 需求结论

需求的最小可交付闭环是：源码公式可追溯、端点错误可复现、模型值不冒充 observed、目录参数不要求用户手工输入、输出边界不越过 EXPLAIN。G4 与 G10 已满足这条闭环；构建耗时模型、生产 recall 和跨架构支持暂不纳入当前通过结论。
