# AI 使用策略自我报告

## 1. 使用范围与责任边界

AI coding agent 用于整理仓库、提出公式和 SQL 草稿、比较工具形态、生成测试矩阵模板、协助全文一致性检查。AI 不连接授权端点、不代替 `psql`、不生成 observed 日志、不决定 G4/G10 通过与否。最终模型、stderr、SHA256、报告数字和提交由人工执行和核对。

## 2. 闭环一：初版 scaling law 错误

早期模型把 samples 的内存按实际 rows 截断，隐含假设所有数组都使用 `N=min(rows,T)`。这会丢掉 `VectorArrayInit()` 按目标容量 `T=max(10000,50*lists)` 立即申请的 `samplesSize`，在 rows<T 或大 lists 场景产生错误 scaling law。旧公式在 100,000/128d/lists=32768 一类场景低估了数量级，在低 lists 场景又可能高估。

修正不是让 SQL “贴合”错误值，而是把 `ivfkmeans.c:277-299` 的 11 项分配逐项抄成可审计函数，并用 `ivfbuild.c:403-415`、`ivfflat.h`、`vector.h` 确认容量、对齐和 ABI。`tools/verify_ivfflat_sizes.c` 在目标 x86-64 环境核出 `vector(128)` item=520 bytes；模型才进入 20 组验证。

## 3. 闭环二：两次数值修正

第一次，评审表把 200,000/384d/lists=8192 估为 6,838 MB。源码显示 samples capacity 是 409,600 而不是实际 200,000 行，模型重算为 7,147 MB；`old-fail-03.log` 真实报错确认 7,147 MB。第二次，100,000/128d/lists=32768 的表值 16,695 MB 被同一语义推翻为 17,459 MB；`old-fail-04.log` 原文报告 17,459 MB。

这两次闭环都包含四步：指出差异、定位源码分配、重算、捕获真实 stderr。AI 初版和评审原值都被当作可检验假设，而不是权威答案；源码语义和后端原文优先。

## 4. 闭环三：被否决的建议

| 建议/候选 | 决定 | 依据 |
|---|---|---|
| 把模型值直接写入 observed | 否决 | 破坏 G4 可证伪性；状态机明确禁止 |
| large 组真实分配 7,147/17,459 MB | 否决 | 3.7 GiB 端点会 OOM；采用 real-threshold 并明确边界 |
| 将 HNSW lists/probes 用 IVFFlat 公式填充 | 否决 | HNSW 不适用这些字段，输出留空 |
| 把 `possible_seqscan` 当 EXPLAIN 结果 | 否决 | 它只表示静态目录风险，生产计划需另测 |
| 把函数做成 pgvector 内部扩展 | 否决 | PR #765 的治理先例；独立 schema 更可维护 |
| 省略 TAP bailout 细节，写成 44 个失败 | 否决 | 真实记录是 0/44、1 bailout、43 未执行 |

## 5. 人工复核与结论

每次 AI 生成的 SQL、公式或文字都经过源码路径检查、端点运行、原始日志对照和边界措辞检查。最终 20/20 的 observed 值来自 stderr，不来自模型；G10 的 `pronargs=0`、HNSW 空字段和事务回滚来自实测输出。AI 提供检索和反例，不能替代验证；本报告保留“blocked/model-only/fail”状态，避免把缺失证据包装成成功。
