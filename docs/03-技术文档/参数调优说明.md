# OpenTenBase pgvector 参数调优说明

## 1. 使用边界

本说明是可执行的调优起点，不是跨数据分布的保证。当前模型验证对象是 `vector`、x86-64 OpenTenBase 5.0/pgvector 0.8.0；构建内存预测对应 pgvector k-means 检查点，不等于整次索引构建的 RSS 上界。生产使用前必须保留业务数据、版本、GUC、EXPLAIN、recall 和延迟记录。

## 2. 建索引前流程

1. 统计并确认 `rows`、`dims`、距离类型和目标 `lists`；对新表先 `ANALYZE`。
2. 用 `sql/02_memory_model.sql` 计算 `predicted_build_memory_mb`，对照当前 `maintenance_work_mem`。
3. 若当前内存低于预测值，优先在建索引会话临时提高 GUC，或降低 lists/分批建索引；不要把整机可用内存全部交给单个并发建索引任务。
4. 用官方 lists 起点建小规模 smoke，再用代表性 workload 选择 probes；预测值通过不代表 recall 已达标。

## 3. lists 与 probes 起点

| 参数 | 起始规则 | 解释 |
|---|---|---|
| `lists`，rows≤1M | `ceil(rows/1000)` | 官方起点，需用业务数据复核 |
| `lists`，rows>1M | `ceil(sqrt(rows))` | 官方起点，限制最大 32768 |
| `probes` | `ceil(sqrt(lists))` | 审计起点，不是 recall 保证 |
| 高 recall 试验 | `probes` 从起点逐步增加到 lists | 同时记录 recall 和延迟 |

G10 实测示例为 1000 行、3 维、IVFFlat `lists=10`：推荐 lists=1、推荐 probes=4。这个输出用于说明公式和目录取参，不意味着 1/4 对所有 workload 都最佳。

## 4. 内存调优

`audit_all_vector_indexes()` 会把 IVFFlat 的预测构建内存与当前 `maintenance_work_mem` 对比。模型将 `samplesSize` 按目标容量 `T=max(10000,50*lists)` 分配，将其他样本数组按 `N=min(rows,T)` 分配；因此不能用实际插入行数简单替换所有数组的容量。

| 结果 | 行动 |
|---|---|
| `maintenance_work_mem` 高于预测值 | 继续检查并发、磁盘和 workload，不自动宣称安全 |
| 低于预测值 | 会话级提高 GUC、降低 lists 或拆分构建；保存新的 stderr |
| 预测值异常大 | 先检查 rows/dims/lists、ABI 和是否误把模型当 RSS |
| HNSW 行 | 不读取 IVFFlat 专属内存列；按 HNSW 自己的 NOTICE/文档处理 |

20 组 G4 矩阵的原始错误证明模型与 pgvector 检查点一致；5 个 large 场景是阈值触发，不证明巨型索引成功构建。

## 5. 建成后零参数体检

执行 `SELECT * FROM pgvector_bench.audit_all_vector_indexes();`。优先查看：索引是否 valid、`reltuples` 是否陈旧、实际 lists 与推荐 lists 的偏离、IVFFlat 内存风险、recommended probes 和 audit_note。HNSW 的 lists/probes/内存字段为空是正确行为，不是缺失数据。

`possible_seqscan=true` 只说明静态目录存在风险，例如索引无效、lists 缺失或超过统计行数；必须用具体业务 SQL 的 `EXPLAIN (ANALYZE, BUFFERS)` 验证是否真的走 Seq Scan。计划和 recall 不能由本工具单独推断。

## 6. 调优记录模板

每次变更记录：数据库版本和 commit、表行数与维度、距离类型、索引参数、`maintenance_work_mem`、probes、查询集合哈希、exact/approx recall、平均/P95/P99（若采集）、计划文本和原始 stderr。一次只改变一个主参数；至少重复三次；结果若只在单机或单一 workload 成立，标注适用域。

## 7. 常见误用

- 把 `predicted_build_memory_mb` 当成整机内存上限。
- 把 `recommended_probes` 当成 recall 保证。
- 把 `possible_seqscan` 当成 EXPLAIN 结果。
- 把 `real-threshold` 写成巨型索引已经成功构建。
- 用旧经验区间覆盖源码模型和后端错误。

这些边界是调优说明的核心：工具给出可解释起点，最终生产结论仍需 workload 实证。
