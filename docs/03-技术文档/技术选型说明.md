# OpenTenBase pgvector 索引诊断技术选型说明

## 1. 工具形态

| 候选 | 选择 | 依据 |
|---|---|---|
| pgvector 扩展内函数 | 否 | PR #765 中维护者不希望为近似公式增加函数 |
| 扩展内 benchmark harness | 否 | PR #863 先例；测试工具与扩展职责分离 |
| 外部 schema + SQL/plpgsql | **采用** | 用户无需编译 ABI，函数可直接阅读，独立投递 |
| C 扩展 | 否 | 诊断正确性不需要新 ABI，增加安装和架构风险 |

外部工具仍可使用 `psql`，但不把诊断逻辑塞进 pgvector 主路径。上游投递时拆成文档与工具 PR，保留源码模型、证据矩阵和边界说明。

## 2. 模型与真值来源

| 候选 | 选择 | 理由 |
|---|---|---|
| 经验拟合公式 | 否 | 旧公式在 8192/32768 lists 场景严重低估 |
| 进程 RSS | 否 | 混入 allocator、worker 和系统开销，不等于 pgvector 报错口径 |
| pgvector 原始 `memory required` 错误 | **采用** | 与 `ivfkmeans.c` 检查点同源，stderr 可归档 |
| 源码逐项 SQL 移植 | **采用** | 11 项分配、容量边界和 +1 取整均可审计 |

large 组用 `real-threshold` 捕获同源错误，避免把 OOM 当作实验结果；observed 缺失时状态只能是 blocked/model-only。

## 3. 参数推荐口径

lists 采用 pgvector 官方起点：rows≤1,000,000 时 `ceil(rows/1000)`，更大时 `ceil(sqrt(rows))`，最后限制在 1..32768。probes 使用 `ceil(sqrt(lists))` 作为起始值，audit 输出的是工作起点，不是 recall 保证。任何生产参数都必须用代表性数据、exact 参照、recall 和延迟矩阵验证。

## 4. 目录与风险输出

目录内省采用 `pg_class.reloptions` 取 lists，`pg_index.indkey` 定位索引列，`pg_attribute.atttypmod` 取维度，`pg_class.reltuples` 取统计行数，`pg_am.amname` 区分访问方法。`possible_seqscan` 只在静态目录明显异常时置 true；输出 audit_note 明确提示要用 EXPLAIN 复核。

## 5. 安全与版本

shell 只接受正整数和受限内存单位，SQL 函数固定 `search_path=pg_catalog,pg_temp`，schema_version 表记录迁移版本。验证 harness 把输入、预测、mode、observed、error、status、stderr 路径绑定到 case id，防止结果列错位或模型回填。

## 6. 未选方案与后续

当前不做生产 EXPLAIN 计划推断、不把 HNSW 套入 IVFFlat 公式、不在 3.7 GiB 端点真实构建 17,459 MB 索引。W3 将利用已有 `pg_stat_progress_create_index` 观测阶段耗时；它必须形成新证据包后才升级 RQ-302。
