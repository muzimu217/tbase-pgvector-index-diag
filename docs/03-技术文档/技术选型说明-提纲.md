# 技术选型说明（提纲・方向二）

## 1. 工具形态选型（本项目最重要的选型）

| 候选 | 依据 | 结论 |
|---|---|---|
| 扩展内 SQL 函数（进 pgvector 上游） | PR #765 被拒；Kane："don't want to add a function for it" | 否 |
| bench harness 形态 | PR #863 被拒 | 否 |
| **外部 SQL 工具集（独立 schema，一键安装）** | 上游治理先例明确接受外部工具生态；用户零安装成本（psql 即可跑） | **采用** |

（此对比表同时是 `06-局限与后续.md` 中"为何不做扩展内函数"一节的素材，T2.10.5。）

## 2. 实现语言选型

plpgsql（纯 SQL 可审计、无编译依赖）vs C 扩展（需匹配 OpenTenBase ABI）→ plpgsql。理由：诊断工具的正确性必须可被用户直接阅读验证。

## 3. 验证方法选型

捕获 pgvector 报错原文 `memory required is X MB, maintenance_work_mem is Y MB` 作为真值来源（T2.2.1），而非观察进程 RSS——报错值就是 pgvector 自己的检查点计算结果，与源码公式同源。

## 4. 数据/口径选型

- 内存单位解析对齐 PG 语义（裸数字 = kB，C1）。
- 取整方式保留源码行为：`totalSize / (1024*1024) + 1`。
