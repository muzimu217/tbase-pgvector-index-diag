# IVFFlat 构建内存模型推导

## 1. 目标与口径

本模型复现 OpenTenBase 内置 pgvector 0.8.0 在 IVFFlat k-means 阶段执行的
内存检查，目标是预测报错中的 `memory required is X MB`，而不是预测进程 RSS。
PostgreSQL 内存上下文管理开销、tuplesort 和并行 worker 内存不在这条报错公式中。

源码锚点：

- `contrib/pgvector/src/ivfkmeans.c:277-299`：11 个分配量、总和及 MB 取整。
- `contrib/pgvector/src/ivfbuild.c:403-415`：目标采样数和样本数组容量。
- `contrib/pgvector/src/ivfflat.h:96-103,291`：`VectorArrayData` 与 `VECTOR_ARRAY_SIZE`。
- `contrib/pgvector/src/vector.h:6,11-17`：vector item 大小。

## 2. 已核验 ABI 常数

在本项目 OpenTenBase x86-64 构建环境中，用实际构建宏编译
`tools/verify_ivfflat_sizes.c`，得到：

| 常数 | 字节 |
|---|---:|
| `sizeof(VectorArrayData)` | 32 |
| `offsetof(Vector, x)` | 8 |
| `MAXIMUM_ALIGNOF` | 8 |
| 128 维 vector 原始 item | 520 |
| 128 维 vector 对齐后 item | 520 |

因此 vector 的 item 大小为 `I = MAXALIGN(8 + 4*dims)`，数组大小为：

```text
VECTOR_ARRAY_SIZE(length, item) = 32 + length * MAXALIGN(item)
```

## 3. 采样数的两个不同口径

设：

```text
T = max(10000, 50 * lists)  -- 目标容量 samples->maxlen
N = min(row_count, T)       -- 实际样本数 samples->length
C = lists                   -- center 数
D = dims
I = MAXALIGN(8 + 4 * D)     -- vector item 字节数
```

`samplesSize` 必须使用 `T`，因为 `VectorArrayInit()` 按目标容量立即分配 items。
`closestCentersSize`、`lowerBoundSize` 和 `upperBoundSize` 使用 `N`，因为它们按
实际样本数创建。这两个口径不能合并。

## 4. 十一个分配量

| 源码变量 | 字节公式 |
|---|---:|
| `samplesSize` | `32 + T * I` |
| `centersSize` | `32 + C * I` |
| `newCentersSize` | `32 + C * I` |
| `aggSize` | `4 * C * D` |
| `centerCountsSize` | `4 * C` |
| `closestCentersSize` | `4 * N` |
| `lowerBoundSize` | `4 * N * C` |
| `upperBoundSize` | `4 * N` |
| `sSize` | `4 * C` |
| `halfcdistSize` | `4 * C * C` |
| `newcdistSize` | `4 * C` |

`lowerBoundSize` 通常是主导项；当实际行数少于目标采样容量时，`samplesSize`
仍按 `T` 分配，也可能成为不可忽略项。

## 5. 总量与报错取整

```text
total_bytes = 上述 11 项之和
required_mb = floor(total_bytes / 1048576) + 1
```

`+1` 来自 `ivfkmeans.c:294-299`，即使总字节恰好是整数 MiB 也会加 1。
因此报告同时展示 `total_mib` 和 `required_mb`，避免把实际字节量与报错口径混淆。

## 6. 首轮 smoke

| rows | dims | lists | total bytes | total MiB | 报错口径 MB |
|---:|---:|---:|---:|---:|---:|
| 100000 | 128 | 100 | 9,476,496 | 9.037 | 10 |
| 100000 | 128 | 1000 | 231,964,096 | 221.218 | 222 |
| 200000 | 384 | 8192 | 7,494,036,064 | 7,146.870 | 7,147 |

任务清单曾给出第三组约 6,838 MB。该值把 `samplesSize` 也按 200,000 行截断，
但源码使用 `samples->maxlen=409,600`；两者相差的约 309 MiB 正是未计入的样本
容量。当前实现以源码语义为准，后续验证矩阵继续用 pgvector 实际报错交叉核验。

## 7. 首条实库核验

在 1000 行、128 维、`lists=1000` 的复制表上，将 `maintenance_work_mem` 设为
1 MB 后创建 IVFFlat 索引：

```text
模型预测：34 MB
实际报错：memory required is 34 MB, maintenance_work_mem is 1 MB
```

创建表、装载模型和建索引均位于同一事务；报错后连接关闭触发回滚，复核测试表
不存在。该案例验证了目标样本容量大于实际行数时的关键分支。

## 8. 适用范围

- 当前 SQL 首版只覆盖 `vector`，不宣称 halfvec、bit 或 sparsevec 已验证。
- 当前 ABI 常数来自 x86-64 OpenTenBase 构建；其他架构须先运行尺寸核验工具。
- 这是 k-means 报错模型，不是整次索引构建的 RSS 上界。
- 完整结论仍需 W2 至少 20 组预测与实测矩阵，硬门槛为误差小于 5%。
